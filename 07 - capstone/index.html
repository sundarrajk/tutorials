Chapter 1 · IT History  ·  The Why

The Internet Broke the Rules

For forty years computing grew predictably. Then four companies opened their doors to the entire planet — and everything that worked before stopped working.

The Pre-Internet World (1950s–1990s)
  • Software served internal users only — hundreds, not millions
  • Load was predictable — batch overnight, office hours interactive
  • Hardware procurement took weeks to months — but that was fine
  • Releases every 6–12 months — coordinated, stop-the-world events
  • One server, one OS, one application — full utilisation by design
The Internet Broke Every Assumption
  • 🛒 Amazon: Black Friday spikes 10–20× overnight. 85% idle the rest of the year.
  • 🔍 Google: 9/11 — global traffic surge in minutes. You cannot plan for this.
  • 📱 Facebook: viral content — millions simultaneously. Unknown before posting.
  • 🎬 Netflix: one hit series = 15%+ of all North American internet traffic.
  • Pattern: vast surplus capacity at off-peak → monetise it → AWS 2006

Chapter 2 · CPU & Virtual Machines  ·  The Hardware Foundation

Moore's Law Built It. Virtualisation Made It Usable.

The cloud is not software magic — it is physics and engineering. Two hardware revolutions made it physically possible to sell compute by the minute.

Revolution 1 — Moore's Law (1965–2023)
  • Transistor count doubled every 18–24 months for 50+ years
  • Intel 4004 (1971): 2,300 transistors · 0.74 MHz
  • Apple M2 Ultra (2023): 134 billion transistors
  • A 58-million-fold increase — the "free lunch" for developers
  • ~2004: clock speed hit the thermal wall at 3.8 GHz · ~130W
  • Industry pivot: fewer, faster cores → more, parallel cores
  • Modern server: 2 sockets × 96 cores = 192 cores, up to 12 TB RAM
Revolution 2 — Virtualisation (VMware 1998)
  • Before VMs: one server = one OS = one app = 5–15% utilisation
  • Hypervisor abstracts physical hardware into virtual hardware
  • One physical server now hosts 10–20 isolated VMs
  • Utilisation jumps from 5% → 60–80% after consolidation
  • Snapshots, templates, vMotion (zero-downtime live migration)
  • VM from template: 5–15 minutes (was 2–6 weeks bare metal)
  • AWS EC2 = "rent a VM by the hour" — virtualisation at global scale

Chapter 3 · Cloud Background  ·  The Operational Reality

The Cloud Solved Provisioning. Not Everything.

Cloud providers eliminated the hardware procurement bottleneck. But the applications, their deployment processes, and the operational habits they encoded were still built for a world of static IPs and weekend maintenance windows.

The On-Premises World Apps Were Built For
  • Fixed IP addresses — every app hard-coded 192.168.1.10:8080
  • 3-tier web (HTTP → App Server → DB) or ESB/SOA hub-and-spoke
  • New server: budget approval → vendor → shipping → racking → OS → months
  • Deployment: Friday midnight, war-room, rollback plan — days of downtime
  • Scaling: physical hardware task, even on VMs required a maintenance window
Why "Lift and Shift" Failed
  • IPs change in the cloud — hard-coded addresses silently broke connections
  • Old apps ran at 30–40% CPU — fine when the server was sunk cost, expensive at pay-per-minute
  • Scaling out to fix inefficiency just multiplied the bill without fixing the code
  • No CLI meant no CI/CD pipeline — still deploying manually
  • Vendor lock-in: proprietary managed services hard to migrate later
  • Conclusion: the cloud gives you elastic hardware. It cannot fix your architecture.

Chapter 4 · Monolith → Microservices  ·  The Redesign

Each Microservices Principle Fixes a Specific Monolith Failure

Chapter 4 is not about technology fashion. Every pattern — bounded contexts, stateless processes, containers, Kubernetes, observability — is a direct engineering response to a specific problem identified in Chapters 1–3.

Problem → Solution Mapping
  • Scale everything to scale one thing → Microservices: each service scales independently (payday: Accounts × 20, everything else × 1)
  • Hard-coded IPs break in cloud → Service discovery + Kubernetes Services (stable DNS, not IPs)
  • One crash = total outage → Isolated services: one pod crash doesn't cascade
  • Release coordination hell → One codebase per service (12-Factor F1): Payments ships Friday, Loans ships Monday
  • "Works on my machine" → Docker: same image on laptop and production (12-Factor F2, F10)
  • Config / secrets in code → Kubernetes ConfigMaps + Secrets (12-Factor F3)
  • Idle servers at off-peak → Kubernetes HPA + Serverless: scale to zero, pay nothing
The New Debugging Reality
  • 8 services × 3 replicas = 24 simultaneous log streams
  • A payment failure spans: Payments → Accounts → Debit Card → Core Banking
  • Which hop failed? Which pod served this request? Which was recycled?
  • Metrics (Prometheus/Grafana): is something wrong right now?
  • Traces (Jaeger/Tempo): where in the call chain is the failure?
  • Logs (Loki/ELK): exactly what went wrong?
  • Factor 11 (logs to stdout) is what makes all three collectible without app-side routing code
The 12-Factor App is not a checklist. It is a coherent philosophy: Factor 3 (config in env) enables Factor 10 (dev/prod parity). Factor 6 (stateless) enables Factor 9 (disposability). Factor 11 (logs to stdout) enables observability. The factors and the platform (Docker + Kubernetes) were designed to run this exact kind of application. Build against the factors; the platform rewards you for free.
Synthesis

Every Layer of the Stack Had to Change

The internet didn't just change one thing — it forced a complete rethink at every level of the computing stack simultaneously. The five presentations map exactly to five layers of that transformation.

Notice the direction of causation: the internet created scale pressure (1) → that pressure demanded elastic hardware (2) → elastic hardware exposed operational rigidity (3) → rigidity demanded architectural redesign (4) → redesigned apps needed a rich managed-service platform (5). Each layer was a necessary consequence of the one below. This is not a history of fashion — it is engineering responding to physics and economics.
Root Cause Analysis

One Cause. Dozens of Inventions.

Every technology we studied — VMs, containers, Kubernetes, microservices, CI/CD, observability — traces back to the same root cause: the internet exposed software to unpredictable, planetary-scale load that no individual organisation could plan for with fixed hardware.

The Old Contract (broken ~1995–2010)
  • Buy hardware upfront for peak load
  • Own and operate your own data centre
  • Static infrastructure, static IPs, manual ops
  • Release infrequently, coordinate everything
The New Contract
  • Rent compute by the second, scale instantly
  • Stateless apps on ephemeral containers
  • Service discovery, not hard-coded addresses
  • Deploy continuously, observe everything
Still Accelerating
  • Serverless: scale to zero, zero idle cost
  • AI/ML as managed APIs (Bedrock, OpenAI, Vertex)
  • Edge computing: logic at the network boundary
  • FinOps: optimise cloud spend as carefully as code

Why This Matters for CS Students

Why Fundamentals Still Win in the Cloud Era

Every abstraction in the modern cloud stack is a direct application of a computer science fundamental. Understanding the fundamentals is what lets you reason about the cloud — not just use it.

🧵 Processes, Threads, Scheduling
  • A Kubernetes pod is a process group. Container isolation is Linux namespaces + cgroups.
  • Horizontal scaling = adding processes. Factor 8 is the OS process model applied at cloud scale.
  • SIGTERM, graceful shutdown = OS signal handling. Factor 9.
🌐 Networking & Sockets
  • Every microservice call is a TCP socket connection. Service discovery replaces static IPs.
  • Load balancers operate at L4 (TCP) and L7 (HTTP). OSI stack is not theoretical.
  • DNS TTL is why hard-coded IPs break in the cloud — IPs change; DNS names don't.
💾 Memory, Storage, Databases
  • The memory hierarchy (registers → cache → RAM → SSD) determines microservice latency budgets.
  • Stateless (Factor 6) = no heap state that can't be reconstructed. Crash safely.
  • ACID transactions, CAP theorem, eventual consistency — all live inside managed cloud databases.
🔒 Concurrency & Consistency
  • Distributed transactions across microservices = the hardest concurrency problem.
  • Message queues (SQS, Kafka) = decoupled producer-consumer with durable buffers.
  • Observability traces = distributed execution timeline across asynchronous services.
⚙️ Compilers, Runtimes, Packaging
  • A Docker image = a hermetically sealed runtime environment (Factor 2). Static linking at cloud scale.
  • JIT compilation (JVM, V8) explains why container startup time matters — JVM warm-up vs GraalVM native.
  • Immutable releases (Factor 5) = version-controlled build artifacts, just like object files.
🔐 Security Primitives
  • TLS everywhere = public-key cryptography applied to every service-to-service call (mTLS in service mesh).
  • IAM roles = capability-based security — least-privilege at cloud scale.
  • Secrets Manager = never commit credentials — the operational consequence of key management fundamentals.
The practitioner advantage: A developer who understands why Kubernetes sends SIGTERM, what a Linux namespace actually is, and why a stateless process is easier to reschedule will make better architectural decisions than one who can only operate the tooling. The cloud commoditised the infrastructure. Fundamentals still differentiate the engineers.
